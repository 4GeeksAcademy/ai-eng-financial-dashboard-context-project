# Convenciones

Análisis de estándares y patrones de codificación observados directamente en el código del repositorio (no se listan reglas aspiracionales sin evidencia).

## Backend (Python / FastAPI)

- **Nomenclatura**: `snake_case` consistente para funciones y variables (`generate_mock_movements`, `filter_movements_by_date`, `build_top_categories`); `PascalCase` para modelos Pydantic y tipos (`FinancialMovement`, `MetricsSummaryItem`, `OperationType`). Funciones "privadas"/helpers internos prefijadas con `_` (`_year_for_month`, `_build_movement`) en [backend/app/routes.py](backend/app/routes.py).
- **Tipado estático completo**: todas las funciones declaran tipos de parámetros y retorno (`-> list[FinancialMovement]`, `-> MetricsFacets`), con `from __future__ import annotations` y sintaxis moderna (`date | None`, `list[...]`) en vez de `Optional`/`List` de `typing`.
- **Modelado de dominio con Pydantic + `Literal`**: los enums de dominio (`OperationType`, `Category`, `BusinessType`, `GroupBy`) se definen como `Literal[...]` en vez de `enum.Enum`, y los contratos de entrada/salida de la API son siempre clases `BaseModel`.
- **Separación por capas dentro de un mismo módulo**: `routes.py` agrupa, en orden, (1) tipos/modelos, (2) generación de datos mock, (3) filtrado, (4) agregaciones, (5) endpoints — sin dividir en subpaquetes (`services/`, `schemas/`, etc.), pese a que el proyecto podría crecer.
- **Funciones puras y testeables**: la lógica de negocio (`filter_movements`, `summarize_movements`, `detect_outcome_alerts`, `calculate_net_value`) está desacoplada de los endpoints FastAPI, que actúan como capa delgada que solo invoca estas funciones y arma la respuesta.
- **Determinismo explícito**: cada endpoint vuelve a llamar `generate_mock_movements(seed=42)` en cada request en lugar de cachear o inyectar los datos, priorizando simplicidad/legibilidad sobre eficiencia.
- **Convención de imports**: bloque único al inicio del archivo, sin agrupamiento por origen (stdlib, terceros, locales) más allá del orden natural (`random`, `collections`, `datetime`, `typing` → `fastapi`, `pydantic`).
- **Pruebas con pytest en estilo "arrange-act-assert" con nombres descriptivos**: `test_<accion>_<condicion_esperada>` (`test_b2b_endpoint_only_returns_b2b_records`, `test_metrics_endpoint_respects_date_filters`) en [backend/tests/test_routes.py](backend/tests/test_routes.py), usando `TestClient` de FastAPI y aserciones directas sobre el JSON de respuesta.
- **Indentación de 4 espacios** y líneas envueltas manualmente en llamadas largas (patrón recurrente de continuar en la línea siguiente tras un paréntesis, p. ej. `random.random(\n) < income_probability`), consistente con el formateo por defecto de `autopep8`/`black` en modo no estricto.

## Frontend (React / TypeScript)

- **Nomenclatura de archivos**: `kebab-case` para todos los archivos de componentes y utilidades (`dashboard-header.tsx`, `income-outcome-chart.tsx`, `financial-utils.ts`), independientemente de que exporten un componente en `PascalCase` (`DashboardHeader`) o funciones en `camelCase` (`computeKPIs`).
- **Componentes funcionales con `export function`** (no `React.FC` ni `export default` en componentes con nombre) — ver [dashboard-header.tsx](frontend/src/components/dashboard/dashboard-header.tsx), [kpi-card.tsx](frontend/src/components/dashboard/kpi-card.tsx). La excepción es `App.tsx`, que usa `export default function App()`.
- **Props tipadas con `interface *Props`**: patrón repetido en todos los componentes (`KPICardProps`, `DashboardHeaderProps`), con props opcionales marcadas (`period?: string`, `loading?: boolean`).
- **Estilo inconsistente de comillas y punto y coma** (hallazgo relevante, no una convención fija): archivos como [App.tsx](frontend/src/App.tsx), [financial-utils.ts](frontend/src/lib/financial-utils.ts) y [financial-types.ts](frontend/src/lib/financial-types.ts) usan comillas dobles `"..."` y punto y coma; otros como [card.tsx](frontend/src/components/ui/card.tsx), [kpi-card.tsx](frontend/src/components/dashboard/kpi-card.tsx) y [dashboard-header.tsx](frontend/src/components/dashboard/dashboard-header.tsx) usan comillas simples `'...'` sin punto y coma. No hay Prettier configurado en [package.json](frontend/package.json) que unifique esto; solo ESLint.
- **Alias de imports `@/`**: configurado en [vite.config.ts](frontend/vite.config.ts) y usado consistentemente en componentes/libs (`@/lib/utils`, `@/components/ui/card`) en vez de rutas relativas largas; sin embargo, dentro de `lib/` se usan imports relativos (`./financial-types`), mezclando ambos estilos según la carpeta.
- **Composición vía `cn()`**: helper en [utils.ts](frontend/src/lib/utils.ts) que combina `clsx` + `tailwind-merge`, usado en todos los componentes visuales para fusionar clases de Tailwind con `className` recibido por props (patrón shadcn/ui).
- **Slots semánticos con `data-slot`**: los componentes de `components/ui/` (p. ej. `Card`, `CardHeader`, `CardContent`) anotan cada elemento con `data-slot="..."`, siguiendo la convención de shadcn/ui para theming/testing por atributo.
- **Mapas de variantes como objeto constante**: patrón `variantStyles: Record<Variant, {...}>` (en `kpi-card.tsx`) en vez de condicionales `if/switch`, para mapear una unión de tipos string a clases de Tailwind.
- **Manejo de estado de carga explícito por componente**: cada componente que consume datos remotos implementa un `if (loading) { return <Skeleton .../> }` antes del render final (`kpi-card.tsx`, `income-outcome-chart.tsx`, `profit-percent-chart.tsx`), en vez de un componente de loading genérico compartido.
- **Tipos de dominio centralizados**: un único archivo [financial-types.ts](frontend/src/lib/financial-types.ts) define los tipos compartidos (`FinancialMovement`, `KPIMetrics`, `MonthlyDataPoint`) usando `type` para uniones y `interface` para formas de objeto — reflejo manual (no generado) de los modelos Pydantic del backend, con el mismo `snake_case` en los campos que replican la API (`create_date`, `operation_type`) pero `camelCase` en los campos calculados en cliente (`totalIncome`, `profitPercent`).
- **Funciones puras y pequeñas en `lib/`**: `financial-utils.ts` separa responsabilidades en funciones de una sola tarea (`toYearMonthKey`, `formatMonthYearLabel`, `computeKPIs`, `computeMonthlyData`, `formatCurrency`, `formatPercent`), todas exportadas individualmente y cubiertas por tests unitarios en `financial-utils.test.ts`.
- **Formato de moneda/fecha con `Intl`**: uso consistente de `Intl.NumberFormat`/`toLocaleDateString` con locale `"en-US"` fijo, en vez de librerías externas de formateo (p. ej. `date-fns`, `dayjs`).
- **Linting**: [eslint.config.js](frontend/eslint.config.js) usa flat config con `@eslint/js` recomendado, `typescript-eslint` recomendado, `eslint-plugin-react-hooks` y `eslint-plugin-react-refresh` (reglas de Vite/Fast Refresh) — no incluye reglas de accesibilidad (`jsx-a11y`) ni Prettier integrado.
- **Testing**: Vitest con sufijo `*.test.ts` junto al archivo que prueban (no carpeta `__tests__` separada), agrupando casos con `describe`/`it` (confirmado en [financial-utils.test.ts](frontend/src/lib/financial-utils.test.ts)).

## Patrones transversales (ambos lados)

- **Datos mock/deterministas en vez de fixtures externos**: tanto el backend (`generate_mock_movements(seed=42)`) como el frontend ([mock-data.ts](frontend/src/lib/mock-data.ts)) generan sus propios datos de ejemplo en código fuente, sin archivos `.json`/`.csv` de fixtures ni base de datos.
- **Sin capa de manejo de errores centralizada**: el backend no define `exception_handlers` personalizados y el frontend captura errores de red con un único `catch` genérico en `App.tsx` que muestra un string fijo, sin categorizar tipos de error.
- **Sin variables de entorno obligatorias**: tanto el proxy de Vite como la ausencia de configuración de base de datos permiten ejecutar el proyecto con `docker compose up --build` sin ficheros `.env`, salvo el caso opcional `VITE_API_BASE_URL`.
- **Ausencia de formateador de código compartido**: no hay `.prettierrc`, `black` config ni pre-commit hooks visibles en el repositorio; el estilo de código depende del criterio de quien escribe cada archivo, lo que explica las inconsistencias de comillas/punto y coma detectadas en el frontend.
